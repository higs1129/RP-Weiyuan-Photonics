# 设备发现与临时路径修复（0.3.12）

“仪器连接”默认收起详细诊断，连接失败后展开。原“连接并启动”保持启动仪器的含义；新“查找这台 RP”只读发现，不启动激光器或更改网络。

填写板卡标签名称，例如 `RP-f0fb33`，点击“查找这台 RP”。软件使用系统名称解析、按物理网卡发送的 mDNS 查询、MAC 邻居记录和有限地址探测；网络路径未验证时，通过已选定的 FT231X CON 串口读取板端 IP、速率和 MAC。
发现指定 RP 需要名称与 MAC 后缀一致，IP 可直接填入原连接框。这里不是全网设备扫描器。

结果区分：

- 已找到且身份、SSH 和系统实际路由已验证：可以点击“连接并启动”。
- 找到地址线索但未通过验证：展示地址来源、各网卡、MAC、SSH、系统所选网卡及 CON 结果。mDNS 名称或缓存邻居表本身不证明目标身份。
- 尚未发现：检查供电、网线、交换机隔离、mDNS 服务/防火墙和 CON 驱动。列出的其他 USB 串口不会被自动当作 RP。
- 多个地址通过验证：不猜测目标，要求明确选择 IP。

## 直连 / 交换机中的 169.254 地址

电脑与 RP 均有 `169.254.*.*` 地址但网段或路由不匹配时，可选择 RP 地址和实际接线的物理网卡，点击“预览临时路径修复”。必须先查找，预览和发现结果各有效两分钟。

预览显示确切目标地址、网卡与当前地址。点击确认后 Windows 请求管理员授权：仅添加该 RP 地址的 `/32` 直连路由（ActiveStore），不修改电脑 IP、掩码、网关、DNS 或板卡网络配置，也不启用 DHCP 服务。软件重新验证实际路由、目标 MAC 与 SSH；失败则撤销本次创建的路由，已有精确路由不覆盖，回滚失败会明确报出。

路由有效至电脑重启。更换地点、重启或 RP 地址变化后重新发现，不永久记住旧 IP。其他固定 IP 网段不自动猜测未占用地址，需要按现场网络规则配置；RP 自身掩码不合适、端口隔离或防火墙阻断时，临时路由也不保证成功。

已连接的实验会话不能执行发现或修复；先结束实验并关闭平台 CMD，再重新打开。浏览器的“Failed to fetch”会单独解释为网页与本机控制服务通信失败，不作为 RP 没有 IP 的证据。

命令行 `network-diagnose.cmd` 沿用根目录 `config.json` 的 `rp_host` / `rp_console_port`，也可显式传 `--host` / `--console-port`；报告使用相同发现逻辑并列出全部串口。它不会修改网络。

## 实现与验证

公共库升级为 `a221-workbench 0.2.35`，唯一实现位于其 `instruments.redpitaya.network_discovery` / `network_route`；应用消费固定 wheel，附带对应源码快照和校验清单。未修改科学模型、标定、激光器启动参数或波形设置。

已进行离线合成 DNS/多网卡/旧邻居/CON/SSH/路由、应用预览令牌和界面交互检查，以及管理员脚本语法与嵌入 C# 编译检查。没有在开发机修改网卡、请求管理员修复或操作真实仪器。实际 Windows 授权、路由添加与现场网络仍需安装后验证。
